01 · Executive summary

What I am asking the school to approve

I developed Aurora as a bilingual information platform for the Student Union. It is intended to make SU information easier to find while giving the school a clearer review and oversight process than a collection of social-media posts alone.

I implemented server-verified school sign-in for school-only features, restrictive Firestore rules, admin-checked server APIs, security response headers, request limits and a photo-download process that creates a unique invisible watermark and an administrator-readable audit record.

I am asking the school to approve the website as a controlled operating model with layered security, logging and school oversight. The school retains owner-level access to the hosting and cloud projects, approve the data-retention policy, approve the use of external service providers and appoint the teacher who can request immediate takedown of content.

For the school

A centrally managed, reviewable place for announcements, event proposals, schedules, student welfare information, financial information and activity records.

For students

One accessible source of information, including for students who do not use Instagram or do not want another social-media account.

For the SU

A consistent publishing workflow, a searchable archive, clearer accountability and a platform that can be handed over to the next cabinet.

For G.T.

A real student-built technology project demonstrating web engineering, cloud services, data governance, cybersecurity and digital project management.

03 · Architecture and defence

How I designed the security layers

The frontend is hosted on Firebase Hosting. Server-side API endpoints run on Vercel. Firestore stores structured records and access rules. Cloudinary stores the gallery assets. Firebase Authentication verifies Google sign-ins. The browser is treated as untrusted: a user interface restriction is never the only protection for a sensitive operation.

LayerImplemented in the sourceWhat it helps protect
Transport and browserHTTPS/HSTS configuration; nosniff; frame restrictions; Referrer Policy; Permissions Policy; Content Security Policy (CSP); API responses use restrictive security headers and no-store caching.Reduces interception and downgrade risk, clickjacking, MIME confusion, unnecessary browser capabilities and some script-injection paths. CSP is a mitigation, not a substitute for safe output encoding.
School authenticationServer-side Firebase ID-token verification, revocation checking, disabled-account checking, verified-email check, Google sign-in provider check and exact @gtcollege.edu.hk school-domain check for school-user features.Prevents a user from gaining school-only access merely by changing frontend JavaScript or supplying an unverified email string.
Admin authorizationAdmin endpoints check a signed Firebase custom claim (admin: true), verify the token and check access to an admin-only Firestore document.Adds server-side privilege checks for publishing, photo upload/deletion and administrative APIs. Hiding the admin link is not treated as security.
DatabaseFirestore rules use a default-deny fallback, with narrow explicit access for school users, administrators and published public news. Sensitive records are not directly writable by ordinary browser clients.Limits direct database access even if someone modifies the page or calls Firebase from a browser console.
Backend APIsBearer-token verification; method checks; input/body validation; ID pattern checks; 256 KB request-body cap in the shared parser; server-side writes for sensitive records; rate limits for key operations.Reduces unauthorized operations, malformed input, oversized requests, automated abuse and direct client manipulation.
Origin policyCORS allows the known Firebase Hosting origins and any explicitly configured additional origin.Restricts which browser origins can read API responses. CORS is not user authentication and does not block command-line clients; tokens and server authorization remain essential.
MediaGallery uploads are signed by an admin-only API and assigned an authenticated Cloudinary asset type. Gallery listing, image delivery and full-resolution download are mediated by authenticated APIs.Reduces public-link exposure and makes school-account checks, rate limiting and auditing possible on gallery access.
Abuse controlsTargeted rate limits include photo downloads (10 per hour per account), feedback (3 per day per account), and limits on gallery, upload-signature, translation, publishing and support endpoints.Reduces routine automated abuse. Application rate limits do not, by themselves, stop a large volumetric DDoS attack.

Example: the school-account access decision

STEP 1Student signs in with Google
STEP 2Server verifies token and status
STEP 3Server checks school domain / role
STEP 4API or Firestore allows the permitted action

A copied URL or modified frontend does not satisfy the server-side token and authorization checks. Access can still be abused if a legitimate account or an administrator's credentials are compromised.

04 · Photo accountability

How I protect event photos and create a traceable download record

I designed the gallery so that school-account authentication is required to list and view gallery photos. Admin-authorized users upload photos through a signed backend workflow. The normal download process is separate from simply viewing a preview.

Current download sequence in the code

01 · SIGN INVerified school account is checked
02 · CONSENTStudent accepts the audit notice
03 · PROTECTServer creates a unique watermark
04 · RECORDServer writes the audit record, then sends the image
  • Identity: the download API checks the authenticated account again; a request without a valid school account (or an authorized admin account) is rejected.
  • Notice: the user must submit consent: true and the current consent version (2026-10-v1). The server does not rely only on a checkbox displayed in the browser.
  • Rate limit: the code limits a school account to 10 photo-download requests per hour.
  • Invisible watermark: the server creates a unique download identifier and embeds a keyed JPEG frequency-domain watermark using DCT-based processing. The payload contains a 64-bit identifier and a CRC-16 integrity check.
  • Audit record: the backend records the account UID, email, display name, photo metadata, download ID, watermark ID/reference, server timestamp, consent version, output details and browser/device category. A keyed network/IP hash is included only when the relevant secret is configured and hashing succeeds.
  • Access to logs: Firestore rules allow administrators to read the download-log collections; browser clients cannot create or modify those records directly.

What the school can investigate

Evidence foundWhat it can establishWhat it cannot establish on its own
A recovered watermark IDIt can be matched to a particular download record and therefore to the account that requested that generated copy.It does not prove that the account holder personally edited or posted the image. Accounts may be shared, borrowed or compromised.
Download log entryIt records that the server generated a protected response for a named account and a particular photo at a recorded time.The current status is response-generated. It is not a receipt proving that the browser completely received, saved or opened the file.
Browser/device categoryIt can indicate broad categories such as Chrome/Edge/Firefox/Safari and desktop/mobile/tablet classification based on the user-agent string.It is not a unique device fingerprint and is not reliable proof of a particular physical device or person.
Optional keyed network hashWhere configured, it can help correlate requests that came from the same network address without storing the raw address in this download record.It is pseudonymous data, not proof of a household or individual; shared networks, VPNs and address changes affect interpretation.
Watermark limitation: I will describe the watermark as a tracing aid, not an unbreakable digital signature. The recovery utility itself warns that screenshots, crops, heavy resizing or re-saving may prevent recovery. Routine edits may leave enough signal to recover an ID, but success depends on how the image was transformed. A recovered ID is useful investigative evidence and must be corroborated with school procedures; a failed recovery does not prove that a student was uninvolved.
Audit-log limitation: the current Firestore log is server-written and administrator-readable, but it is not technically immutable or “tamper-proof”. A sufficiently privileged cloud project owner or service-account holder could alter backend data. I recommend sending a second copy to a separately controlled, append-only audit destination with a defined retention and access policy.

Rapid response procedure for a suspected edited or misused photo

  1. Ask the teacher-in-charge to preserve the reported image, URL, date/time and context. Do not publicly accuse a student based only on a watermark.
  2. Use the watermark extraction utility on the best-quality copy available. Record the extracted ID, confidence and tool version.
  3. Search the administrator photo-download audit by watermark ID/reference and compare the matching photo, account, timestamp, consent version and available metadata.
  4. Preserve the original photo, reported image and relevant logs as separate evidence. Restrict access to the investigation record.
  5. Refer the evidence to the responsible teacher and school. The school—not the website or the developer—decides whether further investigation or disciplinary action is appropriate.
  6. If a photo itself is unsafe to display, an authorized administrator removes it from the gallery and checks the source and derivatives.

06 · Update and approval workflow

How I will prevent unreviewed changes from going live

A. Content workflow

1 · DRAFTContent team prepares text, images, dates and sources
2 · FIRST REVIEWWebsite PIC checks accuracy, completeness and tone
3 · SCHOOL REVIEWTeacher / school reviews sensitive or official content
4 · PUBLISHAuthorized editor publishes; PIC checks the live page

For photographs, the team should also confirm school/event permission, image suitability, caption accuracy and whether a student has raised a concern about publication. For merchant offers, the source, terms and expiry date should be checked. For financial information, the treasurer and teacher should verify figures.

B. Technical workflow

1 · CHANGEI document the code/configuration change
2 · PREVIEWTest on a non-production deployment
3 · VERIFYCheck login, permissions, page behavior and logs
4 · RELEASEDeploy, smoke-test and retain rollback details

For a security-sensitive change, I will test both the permitted and denied cases—for example, a verified school user, a non-school user, a signed-out visitor and an administrator. I will record the commit/deployment reference, the test result and the person who approved the release. The school IT team should independently review changes to authentication, database rules, admin claims and data retention.

Separation of duties: the person who drafts content should not be its only reviewer. I will maintain the platform but will not treat my technical role as approval to publish any content that requires teacher or school approval.

14 · Closing statement

My commitment to the school

I built Aurora to make SU information more accessible and to give the school a practical way to review, supervise and preserve that information. I implemented layered technical controls, including verified school sign-in, restrictive database rules, admin-checked APIs, rate limits and a traceable photo-download workflow.

Because no website is unhackable, I built the system around defence in depth: a watermark is a tracing aid, an audit record is investigative evidence, and security is maintained through correct deployment, account management, monitoring and school oversight.

My proposal is to operate the website with the school as the final authority: I maintain the system, the content team prepares material, the website PIC reviews it first, and the teacher and School IT can approve, audit or remove content. I will document technical updates, test changes before release and escalate security or privacy incidents immediately.

I am asking the school to evaluate the controls, approve the governance process and supervise a student-built platform that I maintain responsibly.

03 · 系統架構及防禦

我如何設計分層保安機制

前端網站由 Firebase Hosting 託管；後端 API 在 Vercel 執行；Firestore 儲存結構化資料及存取規則；Cloudinary 儲存相簿資產；Firebase Authentication 負責驗證 Google 帳戶。我把瀏覽器視為不可信環境：敏感功能不會只依靠前端按鈕或介面限制。

防禦層程式碼中已實作主要保護作用
傳輸及瀏覽器HTTPS／HSTS 設定、nosniff、禁止被嵌入框架、Referrer Policy、Permissions Policy、內容安全政策（CSP）；API 回應亦使用嚴格保安標頭及 no-store 快取控制。降低傳輸攔截及降級、點擊劫持、MIME 類型混淆、不必要瀏覽器功能及部分指令碼注入風險。CSP 是緩解措施，不能取代安全輸出編碼。
校內帳戶驗證伺服器驗證 Firebase ID Token、檢查權杖是否已撤銷、帳戶是否停用、電郵是否已驗證、登入提供者是否為 Google，以及校內功能是否使用精確的 @gtcollege.edu.hk 網域。避免使用者只靠修改前端 JavaScript 或輸入一個校內電郵字串，就取得校內功能權限。
管理員授權管理員 API 檢查已簽署的 Firebase 自訂權限聲明（admin: true）、驗證權杖，並檢查使用者能否讀取只供管理員存取的 Firestore 文件。為公告發佈、相片上載／刪除及管理 API 加入伺服器端權限檢查。隱藏管理員連結並不會被當作真正保安。
資料庫Firestore 規則採用預設拒絕，只為校內使用者、管理員及已發佈公開公告設定有限存取權。一般瀏覽器使用者不能直接寫入敏感紀錄。即使有人修改網頁或在瀏覽器主控台直接呼叫 Firebase，仍會受到資料庫規則限制。
後端 APIBearer Token 驗證、HTTP 方法限制、請求內容驗證、ID 格式檢查、共用解析器的 256 KB 請求內容上限、敏感資料由伺服器寫入，以及主要操作的速率限制。降低未授權操作、格式錯誤輸入、過大請求、自動化濫用及前端直接操控資料的風險。
來源網域政策CORS 只允許指定 Firebase Hosting 網域，以及環境變數中明確設定的其他來源。限制哪些瀏覽器來源可以讀取 API 回應。CORS 並不是使用者驗證，亦不能阻止命令列工具呼叫 API；權杖及伺服器授權仍然必要。
相片資產管理員專用 API 簽署相片上載，並把資產設定為 authenticated 類型。相簿列表、圖片傳送及高解像度下載均經過已驗證的 API。減少公開網址外洩，並令相片存取可以經過校內帳戶檢查、速率限制及紀錄。
濫用防護針對不同功能設定速率限制，包括每帳戶每小時 10 張相片下載、每帳戶每日 3 次意見提交，以及相簿、上載簽署、翻譯、發佈及支持功能的限制。減少一般自動化濫用。但應用程式速率限制本身不能阻止大型流量型 DDoS 攻擊。

04 · 相片問責及溯源

我如何保護活動相片，並建立可追查的下載紀錄

我設計相簿時，要求使用者以校內帳戶登入，才可列出及瀏覽相片。只有獲授權的管理員可以透過簽署後端流程上載相片。一般預覽與下載原檔是兩個不同流程。

目前程式碼中的下載流程

01 · 登入驗證校內帳戶
02 · 同意學生接受下載稽核通知
03 · 保護伺服器建立獨特浮水印
04 · 紀錄伺服器寫入稽核紀錄，再傳送圖片
  • 身分：下載 API 會再次驗證帳戶；沒有有效校內帳戶（或獲授權的管理員帳戶）就會被拒絕。
  • 通知：使用者必須提交 consent: true 及現行通知版本（2026-10-v1）。伺服器不會只依賴瀏覽器上顯示的剔選框。
  • 下載限制：程式碼限制每個帳戶每小時最多提出 10 次相片下載請求。
  • 不可見浮水印：伺服器為每次下載建立獨特識別碼，並透過 DCT 頻域處理在 JPEG 影像中嵌入有密鑰的浮水印。載荷包含 64 位元識別碼及 CRC-16 完整性校驗。
  • 稽核紀錄：後端記錄帳戶 UID、電郵、顯示名稱、相片資料、下載 ID、浮水印 ID／REF、伺服器時間、同意版本、輸出資料及瀏覽器／裝置類別。只有在相關密鑰已設定且雜湊成功時，才會附加鍵控網絡／IP 雜湊。
  • 紀錄權限：Firestore 規則只允許管理員讀取下載紀錄集合；一般瀏覽器不能直接建立或修改這些紀錄。

校方可以調查甚麼

找到的資料可以協助確認甚麼單靠它不能確認甚麼
成功還原的浮水印 ID可與某次下載紀錄配對，從而找出要求伺服器產生該副本的帳戶。不能證明帳戶持有人親自修改或發佈相片。帳戶可能被共用、借用或盜用。
下載稽核紀錄記錄伺服器曾為某個帳戶及指定相片產生受保護的回應，以及相關時間。現時紀錄狀態為 response-generated，並不是瀏覽器已完整接收、儲存或開啟檔案的回執。
瀏覽器／裝置類別可根據 User-Agent 字串記錄 Chrome／Edge／Firefox／Safari 等瀏覽器，以及桌面／手機／平板等大致分類。這不是獨特裝置指紋，不能可靠證明某一部實體裝置或某一個人。
可選的網絡雜湊如已設定，可協助比對來自相同網絡位址的請求，而不會在這筆下載紀錄內直接儲存原始地址。這是可假名化的資料，不是住戶或個人身分證明；共用網絡、VPN 及 IP 變更均會影響判斷。
浮水印限制：我會把浮水印定位為溯源輔助工具，而不是無法破解的數碼簽署。浮水印還原工具本身亦提醒，截圖、裁切、大幅縮放或重新儲存可能令浮水印無法還原。一般修改後可能仍保留足夠訊號，但能否成功取決於圖片如何被處理。還原出的 ID 可作調查線索，必須配合校方程序核實；無法還原亦不代表某位學生一定沒有參與。
稽核紀錄限制：目前 Firestore 紀錄由伺服器寫入並限制管理員讀取，但在技術上並非不可修改或「絕對防篡改」。擁有足夠權限的雲端專案擁有者或服務帳戶持有人，仍有可能更改後端資料。我建議另外將紀錄副本傳送到由不同權限管理的 append-only 稽核儲存位置，並訂明保留及存取政策。

懷疑相片被惡意修改或濫用時的快速程序

  1. 請負責老師保存被舉報的圖片、網址、日期／時間及相關背景。單憑浮水印不應公開指控任何學生。
  2. 使用最佳畫質的可疑圖片執行浮水印還原工具，記錄還原 ID、信心度及工具版本。
  3. 管理員按浮水印 ID／REF 搜尋相片下載稽核紀錄，對照相片、帳戶、時間、同意版本及可用資料。
  4. 分開保存原始相片、被舉報圖片及相關紀錄，限制調查資料的存取權。
  5. 把資料交予負責老師及校方。是否進一步調查或採取紀律行動，應由校方按程序決定。
  6. 如相片本身不適合繼續展示，獲授權管理員應移除相片，並檢查來源檔及衍生圖片。

10 · 資料、私隱及第三方服務

系統會處理哪些資料

我希望校方清楚了解系統會處理哪些資料、處理原因，以及哪些資料需要正式訂立保留期限。

資料／功能目前程式碼行為管治注意事項
相片下載稽核儲存帳戶 UID、電郵、顯示名稱、相片識別資料、下載／浮水印識別碼、時間、同意版本、輸出資料、大致瀏覽器／裝置類別，以及可選的鍵控網絡雜湊。下載處理程式沒有設定過期時間。校方應批准保留期限，並清楚訂明誰可以匯出或調查紀錄。

意見提交API 要求已驗證校內帳戶，並儲存標題、內容、電郵／姓名及審核狀態；程式碼設定 isAnonymous: false。前端說明必須與實際行為一致。真正匿名意見功能需要另行設計及私隱測試。
AI 內容審核／翻譯意見文字會傳送至 OpenRouter 作垃圾訊息審核；管理員要求翻譯時，公告文字亦會傳送至 OpenRouter。這屬第三方資料處理。校方應批准供應商、檢視其資料條款，並提醒使用者不要在意見中提交敏感個人資料。
網站分析收集頁面路徑、瀏覽時間及停留時間。符合資格的使用者登入後，相關瀏覽紀錄可連結其電郵／姓名作管理員活動紀錄。應發布清晰通知、減少不必要的身分連結，並訂明分析資料的保存期限。
公告電郵訂閱儲存校內帳戶電郵、UID、語言及訂閱狀態；公告透過已設定的 Gmail 傳送，並附上簽署取消訂閱連結。限制訂閱紀錄存取權，並支援即時取消訂閱及帳戶移除。
速率限制識別資料部分帳戶／裝置／網絡識別資料會以密鑰雜湊，用於速率限制紀錄；過期資料由程式作非定時清理。雜湊屬假名化，不代表完全匿名。我需要在正式資料庫核實清理及 TTL 設定。

第三方服務供應商

目前項目整合 Firebase（登入、資料庫及託管）、Vercel（後端 API）、Cloudinary（圖片儲存及轉換）、OpenRouter（意見審核及翻譯）及 Gmail SMTP（公告電郵）。校方應批准相關服務及資料流向，確認帳戶擁有權和存取設定，並決定是否需要因私隱或學生保障要求而停用某些功能。

資料保留及私隱發現：我沒有在提供的程式碼中找到一套適用於所有紀錄的保留政策或 TTL 保證。相片下載紀錄的處理程式沒有設定過期時間；支持紀錄明確註明永久保存；頁面瀏覽及速率限制紀錄的程式清理，亦不等同書面保留政策。因此，我建議在正式上線前先由校方批准資料保留政策。

預計可能遇到的危機及處理方法

風險／警號預防方法發生後的處理
1. 已下載相片被修改或在網上濫用。校內帳戶存取、明確下載通知、每次下載浮水印、伺服器紀錄、下載配額及上載前審閱。保存網上圖片及網址；嘗試還原浮水印；把 ID 與下載紀錄配對；保存證據並交老師跟進。不能單憑帳戶配對就斷定誰親自修改圖片。
2. 學生 Google 帳戶被盜用。校內帳戶驗證、學校 IT 帳戶政策及兩步驗證；監察異常下載。請學校 IT 保護／停用帳戶及撤銷工作階段；檢查相關下載紀錄；按校方程序通知老師及受影響學生。
3. 管理員帳戶被盜用或濫用。只保留少量具名管理員、啟用兩步驗證、最小權限、每月檢視名單及獨立校方擁有者帳戶。撤銷管理員權限、停用／重設帳戶、更換受影響密鑰、檢查管理操作；有需要時重新部署，並通知老師及學校 IT。
4. 私人 API Key 或服務憑證外洩。密鑰只存放於供應商環境變數；把環境及憑證檔排除於 Git；啟用密鑰掃描及限制存取。撤銷並更換外洩憑證、重新部署、檢查供應商紀錄、核查未授權操作並記錄事故。
5. 有惡意或過大的圖片上載。只允許管理員取得上載簽署、限制圖片格式、解碼圖片並限制大小／尺寸、驗證資料夾及顯示前審閱。移除圖片及衍生檔、檢查元資料和上載紀錄；有需要時暫停上載功能，並還原安全版本。
6. API 濫用、垃圾訊息或流量突增。按帳戶／IP 設定速率限制、限制輸入長度、驗證帳戶、使用平台級 DDoS 防護及監察流量。暫時限制受影響 API、啟用供應商防護、保留靜態資訊頁面，並透過校方批准的渠道發出服務通知。大型流量攻擊須交由託管供應商處理。
7. 網站或第三方服務中斷。讓部分靜態內容與 API 分開運作、記錄復原聯絡資料，並保存備份及設定文件。確認受影響供應商，透過校方批准渠道通知用戶，從已核實部署／備份還原，並在重開前測試登入及重要 API。
8. 學生個人資料外洩。資料庫預設拒絕、限制管理員存取、減少資料收集、妥善保管密鑰及批准保留政策。即時限制存取、保存紀錄、通知負責老師及學校 IT、評估受影響資料、更換憑證，並依照校方私隱事故程序及適用法律處理。
9. 發佈錯誤、過時或不恰當內容。內容組草擬、PIC 審閱、敏感項目由老師批准、核實資料來源及每月檢查優惠。即時下架或更正；記錄原因；有需要時通知受影響學生，並增加防止重犯的檢查。
10. 意見含辱罵、威脅或學生安全相關內容。要求校內帳戶、設定速率限制、使用內容審核及管理員檢查。限制該提交內容的存取、保存必要證據，並按學校學生保障程序交由負責老師處理；不可只依靠自動審核。
11. AI 審核或翻譯故障／結果錯誤。限制文字長度、使用後備檢查及人工審閱；不把 AI 結果視為最終批准。暫停依賴自動結果，改由人工審閱、更正已發佈文字；有需要時暫停相關 AI 功能。

12 · 為何學生會需要網站

以校方角度出發的實際價值

我並不認為網站要取代 Instagram。我把網站定位為學生會的中央資訊基地：社交媒體可以吸引注意，而網站則負責有系統地整理資訊，讓內容更容易存取、審閱、管理及長期保存。

角度網站帶來的價值對學校的意義
學校把公告、時間表、活動計劃、福利資訊、財政計劃及活動紀錄集中於一處。老師能在同一平台審閱完整內容、發現日期矛盾或計劃不清之處、要求更正及下架不合適內容，減少依賴零散截圖及群組訊息。
學校相簿設有存取控制，以及下載追查紀錄。比起把所有高解像度活動相片公開放在社交平台，提供更受控的發佈方式。這不能阻止截圖或保證追查成功，但可以加強阻嚇及調查能力。
學校學生會屆別之間的資訊延續。活動時間表、已批准計劃、福利安排及交接資料可以持續有系統地保存，不會只留在個別學生的社交帳戶內。
學校學生主導的科技開發。項目展示 G.T. 學生在網頁開發、雲端架構、身分驗證、API、資料處理、圖片技術、網絡保安及專案管治方面的 STEM 能力。
學生只要有一般瀏覽器便可開啟資訊，毋須擁有 Instagram 帳戶或安裝社交媒體應用程式。照顧沒有使用 Instagram、不想開設帳戶或不方便瀏覽社交媒體動態的同學，讓所有同學更公平地取得資訊。
學生新聞、活動、時間表、福利、財政及相片均有清晰分類。同學可以在需要時主動尋找優惠或活動細節，而毋須不斷翻查舊帖文。
學生會更專業的溝通方式、更清晰的更新責任及可累積的運作紀錄。內閣能更一致地發佈資料、減少重複查詢、收集有系統的意見，並為下一屆留下有用紀錄。

如何展示 G.T. 的 STEM 能力

我把這個項目建立為一個真正運作的系統，而不是一張靜態宣傳海報。它結合響應式前端開發、中英雙語使用體驗、雲端託管、Google 身分驗證、資料庫授權、無伺服器 API、圖片處理、浮水印、分析工具及保安營運。只要有老師監督並妥善處理私隱，它可以成為學生把 STEM 知識應用於真實校園需要的具體例子。

這個提案不只是「讓學生會有一個網站」，而是「為學校建立一個由學生開發、受校方監督、可搜尋及可持續維護的數碼渠道，提升資訊流通，同時展示負責任地使用科技的能力」。

14 · 總結

我對校方的承諾

我建立 Aurora，是希望令學生會資訊更容易取得，亦讓校方有實際方法審閱、監督及保存相關資訊。我已在提供的項目中實作多項有意義的技術措施，包括校內帳戶驗證、嚴格資料庫規則、管理員 API 權限檢查、速率限制，以及可追溯的相片下載流程。

我亦清楚了解系統的限制：沒有網站可以保證永不被入侵；浮水印不能保證在所有圖片處理後仍可還原；下載紀錄不能單獨證明誰親自修改圖片；而保安亦取決於正確部署、帳戶管理、資料保留、持續監察及校方監督。

我的建議是讓校方成為網站的最終管理及監督者：由我維護系統，內容組準備資料，網站 PIC 先作初審，再由老師及學校 IT 按需要批准、審閱或要求下架。我會記錄技術更新、在發佈前測試修改，並即時上報保安或私隱事故。

我並不是要求校方相信網站不可能被入侵，而是希望校方檢視現有措施、批准管治流程，並在監督下運作一個由學生開發、可以持續改善及負責任地維護的平台。
