1. Executive Summary

As the lead developer of the Aurora web platform, I have designed and engineered this system from the ground up prioritizing security discipline, data privacy, and robust access control. Unlike standard web projects that rely on weak client-side controls, I have implemented a server-enforced, defense-in-depth security architecture built on zero-trust principles, where all security decisions, user authentication, and data authorizations are enforced strictly on the server.

Key security highlights I implemented include:

  • Server-Side Authorization & Strict Domain Locking: Every privilege request is validated on the server side using Firebase Admin SDK and cryptographic JWT verification, enforcing exclusive access for verified @gtcollege.edu.hk accounts.
  • Database Hardening: Firestore database rules operate on a strict default-deny framework, blocking unauthorized browser reads or writes.
  • Private Asset Architecture & Digital Traceability: Photo originals are hosted strictly in authenticated private storage and are never exposed via direct public URLs. Before any download, the student must read and accept a download-audit notice. Every delivered photo then carries an invisible frequency-domain (DCT) watermark that encodes a unique download identifier, while a tamper-resistant audit record is written on the server (written only by the server, readable only by administrators).
  • Proactive Defense-in-Depth: The application incorporates strict Content Security Policy (CSP) headers, HTTP Strict Transport Security (HSTS), revocation-aware token verification, automated rate limiting, anti-spam artificial intelligence filters, and HMAC IP anonymization.

The Aurora website is hardened, designed to resist intrusion, and engineered to safeguard student data and media assets. This report also sets out how the platform is operated, monitored and overseen by the school (Sections 7–11).

3. Photo Distribution & Traceability Infrastructure

To satisfy the school's requirements for secure photo distribution, I designed a complete traceability system that ties every downloaded photo directly to the authenticated user who requested it. It combines an explicit download acknowledgement, an invisible frequency-domain watermark and a tamper-resistant audit log.

How I Built the Traceability Engine

  1. Mandatory Identity Verification: A student must authenticate using their official school Google account (@gtcollege.edu.hk).
  2. Download Audit Acknowledgement: Before any file is prepared, the student is shown a notice explaining that their download digital footprint will be audited, and must tick an agreement box to continue. The server independently rejects any download request that does not carry the accepted notice version, and the acceptance is stored in the audit record.
  3. Invisible Frequency-Domain Watermarking: When the request is accepted, my serverless API (/api/photo-download) retrieves the original from private storage and embeds the watermark entirely in memory before the file reaches the browser.
    • Technique: The image is divided into 8×8 pixel blocks and transformed with the Discrete Cosine Transform (DCT) — the same mathematics used by JPEG. A unique download identifier is embedded into mid-frequency coefficients using quantization index modulation, following a secret-key pattern known only to the server. The change is visually imperceptible; no visible mark is placed on the photo.
    • Payload: a 64-bit download identifier plus a CRC-16 integrity check, repeated thousands of times across the whole image so the mark is recovered by statistical voting rather than from any single location.
    • Robustness: because the identifier lives in the frequency components of the image rather than in specific pixels, it is designed to survive JPEG compression, resizing, format re-saving and cropping. Recovery is performed offline with the Aurora watermark reader, which realigns the block grid automatically.
    • Fail-closed delivery: if the watermark cannot be applied, no file is delivered.
  4. Tamper-Resistant Audit Logging: Concurrently, the server creates a tamper-resistant log in the photoDownloadLogs collection, accessible only by high-level administrators.
    • Log Record Contains: Server timestamp, full verified email, user UID, display name, photo metadata, unique downloadId, watermarkId, watermarkRef, consent version and time, batch tracking ID, device/browser profile, and keyed IP hash.
  5. No Residual Copies: Watermarking is performed in memory and the result is streamed straight to the student, leaving no public URLs or accessible static assets behind.

Rapid Traceability Protocol

If a photo is ever flagged for misuse or unauthorized distribution, I have established a clear 4-step identification procedure for School IT and administrators:

  1. Read the Watermark: Run the suspect image through the Aurora watermark reader (scripts/extract-watermark.js), which recovers the embedded download identifier and its REF code.
  2. Query System Logs: Open the Admin → Photo Downloads dashboard or search photoDownloadLogs using the recovered REF or watermarkId.
  3. Match Account Metadata: Retrieve the complete identity details tied to that exact download instance (Full Email, UID, HKT Download Time, Device Fingerprint, and the recorded acceptance of the audit notice).
  4. Export Verification Evidence: Export the single cryptographically timestamped audit log row to confirm downloader accountability.

Scenario: A Downloaded Photo Is Edited and Posted Online

This is the school's key concern, so here is exactly what the school can do:

SituationWhat the school can trace
A. The image is re-posted unchanged or after typical edits (filters, text overlays, re-compression). Run the watermark reader → the embedded identifier is recovered → search photoDownloadLogs → the verified school account, UID, time and device profile of that exact download are identified, typically within minutes.
B. The image was resized, cropped or saved in a different quality. The identifier is spread across the entire image in the frequency domain, so it remains recoverable from the surviving area; the reader realigns the block grid automatically and can test the common download resolutions.
C. The image was shared onwards by someone who never downloaded it. The embedded identifier still points to the account that originally downloaded the file, giving the school the start of the chain to follow under its own procedures.

Acknowledgement and escalation layer — every student accepts the download audit notice before downloading, including the statement that edits which harass, mock or misrepresent others breach the school's code of conduct. The agreed escalation path is: IT/administrator retrieves the log row → Teacher-in-Charge → school disciplinary process. Log access is for investigating misuse only.

Together, the invisible technical trail and the mandatory acknowledgement act as both deterrence (students know a download is attributable) and evidence (the school can establish who downloaded what, and when).

4. Operational Safety & Maintenance Routines

To ensure operational security remains uncompromised throughout the term, I have established strict operational protocols and maintenance routines:

  • Pre-Launch System Audit: Comprehensive verification of Vercel environment variables, Firebase security rules deployment, and active TTL execution policies.
  • Access Control Maintenance: Monthly review of admin lists via /api/list-admins. Any individual leaving the team has their claims and active tokens revoked immediately using automated service account scripts (scripts/set-admin-claims.js --revoke).
  • Secret Management & Hygiene: All sensitive API keys, service account credentials, and SMTP passwords are stored securely in Vercel environment variables, completely excluded from source code repositories.
  • Administrative Code of Conduct: All platform administrators must enforce mandatory 2-Step Verification (2SV) on their Google accounts, conduct administrative duties exclusively on secured devices, and adhere to strict data protection standards regarding log exports.

The day-to-day, weekly, monthly and per-term routines that keep these controls working while the site is live are listed in Section 9.3 (Monitoring Routines), and the handling of foreseeable incidents is in Section 10.

10. Foreseeable Risks & Response Plan

We have anticipated the crises a student-run school website is most likely to face. For each, we state how we prevent it and what we do if it happens.

10.1 Standard Incident Response

  1. Detect: via audit logs, routine checks, a user report or a teacher's report.
  2. Contain: immediately unpublish the content, disable the affected feature, or revoke affected tokens/admin claims.
  3. Assess: identify what happened, which data or accounts were involved, and whether personal data is affected.
  4. Notify: inform the Teacher-in-Charge and School IT, and affected persons where appropriate; the school decides on any disciplinary or external reporting.
  5. Recover & learn: restore service, rotate secrets if needed, record the incident, and fix the root cause.

10.2 Risk Register

3. 相片發佈與溯源基礎設施

為滿足學校對安全相片發佈的要求，我設計了一套完整的溯源系統，將每一張被下載的相片直接連結至要求下載的已驗證使用者。系統結合明確的下載確認、不可見的頻域浮水印及防篡改稽核紀錄。

我如何建構溯源引擎

  1. 強制身分驗證： 學生必須使用其官方學校 Google 帳戶（@gtcollege.edu.hk）進行驗證。
  2. 下載稽核確認： 在準備任何檔案之前，系統會向學生顯示通知，說明其下載數碼足跡將被稽核，學生必須剔選同意方可繼續。伺服器亦會獨立拒絕任何未附帶已接受通知版本的下載請求，並將同意紀錄存入稽核紀錄。
  3. 不可見頻域浮水印： 請求獲接受後，我的無伺服器 API（/api/photo-download）會從私人儲存取回原檔，並在檔案送達瀏覽器之前，完全於記憶體內嵌入浮水印。
    • 技術： 影像被分割為 8×8 像素區塊，並以離散餘弦變換（DCT）（與 JPEG 相同的數學原理）處理。獨特的下載識別碼會以量化索引調變方式嵌入中頻係數，並依循僅伺服器知悉的密鑰圖樣。改動在視覺上無法察覺；相片上不會出現任何可見標記。
    • 載荷： 64 位元下載識別碼加 CRC-16 完整性校驗，並在整張影像中重複數千次，因此可透過統計投票而非單一位置還原浮水印。
    • 強韌性： 由於識別碼存在於影像的頻率成分而非特定像素，因此設計上可抵受 JPEG 壓縮、縮放、重新儲存格式及裁切。還原工作由離線的 Aurora 浮水印讀取工具執行，並會自動重新對齊區塊網格。
    • 失敗即停止送出： 若無法套用浮水印，則不會送出任何檔案。
  4. 防篡改稽核紀錄： 同時，伺服器會在 photoDownloadLogs 集合中建立防篡改的紀錄，僅限高階管理員存取。
    • 紀錄內容包括： 伺服器時間戳、完整已驗證電郵、使用者 UID、顯示名稱、相片元資料、獨特 downloadId、watermarkId、watermarkRef、同意版本及時間、批次追蹤 ID、裝置／瀏覽器資訊，以及鍵控 IP 雜湊。
  5. 不留任何副本： 浮水印處理於記憶體內完成，結果直接傳送給學生，不留任何公開網址或可存取的靜態資產。

快速溯源程序

若任何相片被標記為濫用或未經授權散佈，我已為學校資訊科技部及管理員訂立清晰的四步識別程序：

  1. 讀取浮水印： 將可疑影像交由 Aurora 浮水印讀取工具（scripts/extract-watermark.js）處理，還原嵌入的下載識別碼及其 REF 代碼。
  2. 查詢系統紀錄： 開啟 管理員 → 相片下載 儀表板，或使用還原的 REF 或 watermarkId 搜尋 photoDownloadLogs。
  3. 配對帳戶元資料： 取回與該次下載完全對應的完整身分資料（完整電郵、UID、HKT 下載時間、裝置指紋，以及已紀錄的下載通知同意）。
  4. 匯出驗證證據： 匯出該筆具密碼學時間戳的稽核紀錄，以確認下載者責任。

情境：已下載的相片被修改並發佈到網上

這是校方最關心的問題，以下清楚說明校方可以做到甚麼：

情況校方可追查的資料
A. 圖片原樣或經常見修改（濾鏡、加文字、重新壓縮）後被重新發佈。 運行浮水印讀取工具 → 還原嵌入的識別碼 → 搜尋 photoDownloadLogs → 即可確定該次下載的已驗證學校帳戶、UID、時間及裝置資訊，通常數分鐘內完成。
B. 圖片被縮放、裁切或以不同畫質重新儲存。 識別碼以頻域方式分佈於整張影像，因此可由餘下範圍還原；讀取工具會自動重新對齊區塊網格，並可測試常見的下載解像度。
C. 圖片由從未下載過的人轉發。 嵌入的識別碼仍會指向最初下載該檔案的帳戶，為校方提供可按其自身程序追查的起點。

確認與升級層面 — 每位學生在下載前均須接受下載稽核通知，其中包括「以騷擾、嘲弄或扭曲他人形象為目的的修改，違反校規」的聲明。既定升級途徑為：資訊科技組／管理員檢索紀錄 → 負責老師 → 校方處分程序。紀錄僅供調查濫用之用。

不可見的技術足跡與強制確認合併，既產生阻嚇作用（學生知道下載可被追溯），亦提供證據（校方能確認誰在何時下載了甚麼）。

10. 可預見風險與應變計劃

我們已預想學生自行營運的校園網站最可能面對的危機。每一項均說明如何預防，以及一旦發生時如何處理。

10.1 標準事故應變流程

  1. 偵測：透過稽核紀錄、恆常檢查、用戶舉報或老師通報。
  2. 遏止：立即下架內容、停用受影響功能，或撤銷受影響的權杖／管理員聲明。
  3. 評估：確定事件經過、涉及的資料或帳戶，以及是否影響個人資料。
  4. 通報：通知負責老師及學校 IT，並在適當時通知受影響人士；是否作出處分或對外通報，由校方決定。
  5. 復原與檢討：恢復服務，需要時更換密鑰，記錄事件，並修正根本原因。

10.2 風險登記表

風險預防措施一旦發生
1. 相片被濫用或在網上被惡意修改 學校帳戶登入；強制下載稽核通知；載有獨特下載 ID 的不可見浮水印；逐次下載稽核紀錄；下載配額。 讀取嵌入的浮水印或按相片／時段搜尋追查（第 3 節）→ 負責老師 → 校方程序；有需要時移除相簿／相片；支援受影響學生。
